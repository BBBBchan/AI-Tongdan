## 运行条件与部署选择

| 部分 | 条件 |
| --- | --- |
| Web 应用 | Python 3.10 或以上、FFmpeg、ffprobe、可访问 Bilibili 的网络 |
| 浏览器 | 支持现代 JavaScript 和 HLS.js；Chrome/Edge 等现代浏览器均可尝试 |
| 已有模型 API | Web 应用不需要本机 GPU；模型在其他机器运行即可 |
| 自部署视觉模型 | Linux、兼容 CUDA 的 NVIDIA GPU、适合模型与上下文的显存 |
| 自部署音频模型 | 独立 Python 环境；默认 GPU 转写、CPU VAD/声纹，详见部署文档 |
| 远程访问 | 推荐 SSH 本地端口转发；浏览器访问本机转发端口 |

建议先选择一种方式：

- **已有模型服务**：只安装 Web 应用，填写模型接口，最快开始使用。
- **自行部署完整模型**：先启动 Web 应用，再按 [模型部署指南](deployment.md) 下载权重并启动视觉、音频服务。
- **先体验直播页面**：暂不设置模型接口，仍可尝试视频和弹幕；观察与问答会显示等待模型，不会伪造理解结果。

现有视觉部署在 H200 上验证过。FP8 减少权重显存占用，但不同 GPU 对 FP8、上下文长度和并发的支持不同，不能仅按模型参数量判断是否可运行；本项目未对所有显卡做兼容性验证，也不将 FP8 宣称为相对 BF16 的确定加速结论。权重、Python 环境和会话记录均不随 Git 仓库分发。

## 下载代码

本仓库当前为私有仓库，需要先获得访问权限并登录对应 GitHub 账号。**GitHub 登录凭据只用于下载代码，与 Bilibili Cookie 是两回事。**

### 方法一：GitHub CLI

先安装 Git 与 GitHub CLI，然后执行：

```bash
gh auth login
gh repo clone BBBBchan/AI-Tongdan
cd AI-Tongdan
```

`gh auth login` 会引导交互式登录，不需要把访问令牌写入 README、Git remote URL 或应用配置。

### 方法二：SSH

如果 GitHub 账号已配置 SSH key：

```bash
git clone git@github.com:BBBBchan/AI-Tongdan.git
cd AI-Tongdan
```

### 方法三：HTTPS 或 ZIP

```bash
git clone https://github.com/BBBBchan/AI-Tongdan.git
cd AI-Tongdan
```

HTTPS 使用本机 Git 凭据管理器完成认证。也可以在已登录且有权限的浏览器中打开 [仓库首页](https://github.com/BBBBchan/AI-Tongdan)，选择 **Code → Download ZIP**，解压后进入目录。

ZIP 下载适合只运行应用；如果希望后续更新，建议使用 Git。私有仓库无权限时的 404 不表示下载命令有误。

<a id="install"></a>

## 安装并启动应用

### 1. 安装 Python 和 FFmpeg

<a id="windows"></a>

**Windows：先进入 Ubuntu，再按下方 Linux 命令操作。** 仓库脚本使用 Bash，推荐 Windows 11 或支持 WSL2 的 Windows 10；原生 Windows 没有完整验证。

在开始菜单搜索 **PowerShell**，右键选择“以管理员身份运行”，执行：

```powershell
wsl --install -d Ubuntu
```

如果系统提示重启，先重启电脑，再从开始菜单打开 **Ubuntu**。首次打开时按提示设置 Linux 用户名与密码；输入密码时不显示字符是正常现象。后续本文的 Bash 命令都在这个 Ubuntu 窗口运行，而不是 PowerShell。代码也建议放在 Ubuntu 用户目录内，例如 `~/AI-Tongdan`；安装完下方依赖后，可按[下载代码](#download)在 Ubuntu 内重新下载。

<a id="linux"></a>

**Ubuntu / Debian：**打开“终端”，逐段执行：

```bash
sudo apt-get update
sudo apt-get install -y python3 python3-venv python3-pip ffmpeg git
python3 --version
ffmpeg -version
ffprobe -version
```

确认 Python 至少为 3.10。系统发行版过旧时，请自行使用合适的新版本 Python 创建环境。

<a id="macos"></a>

**macOS：**打开“终端”，先确认已安装 [Homebrew](https://brew.sh/)，再执行：

```bash
brew install python@3.11 ffmpeg git
python3.11 --version
ffmpeg -version
ffprobe -version
```

这几个版本检查能正常显示内容，才说明运行环境已经装好。`command not found` 表示对应命令还没安装好，不能直接跳过。

### 2. 创建独立环境

先进入下载或解压得到的项目文件夹。确认里面有 `start.sh`、`requirements.txt` 与 `.env.example`。Linux / WSL 使用下面命令；macOS 将第一行改为 `python3.11 -m venv .venv`：

```bash
python3 -m venv .venv
.venv/bin/python -m pip install --upgrade pip
.venv/bin/python -m pip install -r requirements.txt
```

如果暂时不安装测试和浏览器自动化依赖，只需 `requirements.txt`。视觉模型和音频模型不要装进这个轻量 Web 环境。

### 3. 创建配置文件

首次运行才复制模板；如果已经有 `.env`，保留原文件并编辑，避免覆盖已填的接口或登录信息。以点开头的文件可能在文件管理器中被隐藏，在终端仍能正常编辑。

```bash
cp .env.example .env
```

使用文本编辑器打开 `.env`，或在终端执行 `nano .env`。在 nano 中按 `Ctrl+O`、回车保存，按 `Ctrl+X` 退出。它是配置文本，不需要运行，也不要执行 `source .env`。

最少可以先保留：

```dotenv
FFMPEG_BIN=ffmpeg
DATA_DIR=data
AUDIO_ENABLED=1
SAMPLE_INTERVAL=1
OBSERVATION_FRAMES=4
OBSERVATION_STRIDE=3
OBSERVATION_CONCURRENCY=2
AUDIO_ALIGNMENT_WAIT_SECONDS=0.5
ADAPTIVE_OBSERVATION=1
OBSERVATION_MAX_FRAMES=8
OBSERVATION_TARGET_LAG=15
```

若 FFmpeg 不在 PATH，将 `FFMPEG_BIN` 改为其真实绝对路径；同目录最好有 `ffprobe`，否则需保证 `ffprobe` 可从 PATH 找到。

### 4. 启动

```bash
./start.sh
```

看到终端提示 Uvicorn 正在 `http://127.0.0.1:7862` 运行后，保持这个终端打开，浏览器打开 **http://127.0.0.1:7862**，输入正在开播的直播间网址并连接。Windows / WSL 也在 Windows 的浏览器打开这个地址。播放器默认静音，点击播放器音量控件开启声音。

第一次使用可以暂不填模型，但 AI 功能会等待模型就绪；已有模型接口时继续[下一节](#model-api)。连接按钮只连接直播，不会替你下载或启动大模型。

`start.sh` 在 `.venv` 不存在时也会尝试创建环境、安装应用依赖；首次部署建议手动完成前述步骤，便于发现 Python 或网络问题。

如果希望修改端口：

```bash
HOST=127.0.0.1 PORT=7863 ./start.sh
```

**HOST / PORT 必须通过启动命令的环境变量设置。** 当前 `start.sh` 在应用加载 `.env` 之前确定监听地址，因此仅修改 `.env` 中的 HOST / PORT 不会改变 Uvicorn 监听地址。

### 5. 确认服务状态

```bash
curl http://127.0.0.1:7862/api/health
```

应返回 `ok: true`，并展示 FFmpeg 与模型是否配置。`configured` 仅表示配置存在，**不等于模型已通过实际推理**；页面上的模型检查会执行真实红/蓝双图请求。

<a id="model-api"></a>

## 接入已有模型 API

### 视觉模型

编辑 `.env`：

```dotenv
MODEL_BASE_URL=http://127.0.0.1:8020/v1
MODEL_NAME=Qwen3.8-27B-FP8
MODEL_API_KEY=replace-with-your-own-vision-api-key
MODEL_TIMEOUT=90
```

`MODEL_BASE_URL` 包含 `/v1`。服务需要支持：

- OpenAI-compatible `/chat/completions` 接口；
- 一次输入多张 `image_url` 图片；
- JSON 对象输出；
- 当前适配器使用的 `chat_template_kwargs.enable_thinking=false`。

并非所有“兼容 OpenAI”的服务都支持上述模型参数；接入其他供应商时，可能需要调整 [app/model.py](../app/model.py)。默认观察从 4 帧开始，在 2–8 帧之间自适应调整，问答最多回看 4 张缓存帧。

### 音频模型

编辑 `.env`：

```dotenv
AUDIO_ENABLED=1
AUDIO_BASE_URL=http://127.0.0.1:8021
AUDIO_API_KEY=replace-with-your-own-audio-api-key
```

音频地址不带 `/v1`。应用将请求 `/analyze`，提交 16 kHz 单声道 WAV 的 Base64，接收带时间、文本与可选声纹的结果。这不是通用的 `/audio/transcriptions` 接口；请使用仓库提供的服务，或实现相同协议。模型下载、接口与验证见 [GPU 模型部署指南](deployment.md)。

若暂时没有音频服务：

```dotenv
AUDIO_ENABLED=0
```

网页播放的直播原声仍由 HLS 保留；关闭的是后台转写，不是播放器声音。

### endpoint 文件方式

也可以不在 `.env` 写明 API key，而使用本地 endpoint JSON 及独立密钥文件。默认位置：

- `data/model_endpoint.json`
- `data/audio_endpoint.json`

视觉示例：

```json
{
  "base_url": "http://127.0.0.1:8020/v1",
  "model": "Qwen3.8-27B-FP8",
  "api_key_file": "secrets/vision_api_key.txt"
}
```

音频示例：

```json
{
  "base_url": "http://127.0.0.1:8021",
  "model": "Qwen3-ASR-0.6B + CAM++",
  "api_key_file": "secrets/audio_api_key.txt"
}
```

相对 `api_key_file` 路径以 **endpoint 文件所在目录** 为基准。非空 `MODEL_BASE_URL` / `AUDIO_BASE_URL` 优先于对应 endpoint 文件，且不会再从该文件补齐密钥；填写 URL 时需同时填写对应 key。已在启动终端导出的同名环境变量通常优先于 `.env`。修改配置后正常重启应用，活动会话会尝试恢复。

`.env`、`data/`、密钥和 endpoint 文件均被 `.gitignore` 排除，不应提交到仓库。

<a id="self-hosted-models"></a>

## 自己下载与部署模型

没有现成接口、打算使用自己的 NVIDIA GPU 时，按 **[GPU 模型完整部署指南](deployment.md)** 操作。指南包含硬件检查、权重下载、独立环境、视觉 / 音频服务启动、密钥生成、接口验证和排障。

默认视觉模型为 `Qwen/Qwen3.8-27B-FP8`，音频组件为 `Qwen3-ASR-0.6B`、Silero VAD 与 CAM++。网页、视觉和音频环境分别安装，避免依赖冲突。模型可以在同一台 GPU 机器或不同机器运行，网页应用只需能访问接口。

如果想先确认下载计划，可在项目根目录执行：

```bash
python3 -m venv .venv-download
.venv-download/bin/python -m pip install -r deploy/requirements-download.txt
.venv-download/bin/python deploy/download_models.py --component all --dry-run
```

`--dry-run` 只显示计划，不会下载大文件，也不表示模型已部署。真正下载与启动前先阅读指南中的磁盘、GPU 和环境要求；不要把模型依赖直接装进网页应用的 `.venv`。

<a id="remote-access"></a>

## 远程机器部署与访问

### 推荐：只向本机转发网页端口

在服务器上正常运行 `./start.sh`，在个人电脑终端执行：

```bash
ssh -N -L 7862:127.0.0.1:7862 your-user@your-server
```

个人电脑浏览器访问 `http://127.0.0.1:7862`。这样不需要把带有直播记录、声音参考和发送权限的工作台直接暴露在公网。

### 应用和模型分别位于不同机器

例如 Web 应用在电脑，模型在 GPU 服务器，可转发两个推理端口：

```bash
ssh -N \
  -L 8020:127.0.0.1:8020 \
  -L 8021:127.0.0.1:8021 \
  your-user@your-gpu-server
```

Web 配置仍填写本机 `8020/8021`，同时使用与服务端一致的 API key。模型监听地址、转发目标和认证必须对应。

### 后台运行、停止与更新

可以通过 tmux 等终端会话管理工具保持进程运行：

```bash
tmux new -s ai-tongdan
./start.sh
```

终端内 `Ctrl+C` 正常关闭 Web 服务，保留活动会话恢复指针。网页点击“断开”则主动停止会话并清除恢复指针。

更新代码前先正常停止 Web 服务：

```bash
git pull --ff-only
.venv/bin/python -m pip install -r requirements.txt
./start.sh
```

Web 应用、视觉服务与音频服务是独立进程，停止 Web 不会自动释放模型服务器的 GPU。完整停机时分别关闭对应服务。

若自行设置 `HOST=0.0.0.0` 并通过反向代理访问，需要自行配置 HTTPS、访问鉴权和 SSE 流式代理；当前应用不是多用户隔离平台，多个访问者共享会话与已配置的发送账号。优先使用本地监听加 SSH 转发。

<a id="bilibili-cookie"></a>

## 绑定自己的 Bilibili Cookie

**观看和接收访客弹幕通常不要求登录；向直播间发送弹幕需要你自己的 Bilibili 登录状态。** Cookie 失效、平台验证、直播间禁言或账号限制仍由 Bilibili 决定。

### 获取本人 Cookie

#### 方法一：用本地脚本导出

仓库根目录提供 [get_bilibili_cookie.py](../get_bilibili_cookie.py)。先在浏览器登录自己的 B 站账号，然后在**这台浏览器所在的电脑和系统**运行脚本。应用部署在远程服务器时，仍在自己的电脑导出，再把文件内容粘贴到应用页面；远程服务器无法直接读取本机浏览器 Cookie。

在终端进入脚本所在文件夹，逐行执行：

```bash
python3 -m pip install -U browser-cookie3
python3 get_bilibili_cookie.py --browser chrome
```

**Windows 浏览器请在 Windows 的 PowerShell 中运行此脚本**，不要在 WSL / Ubuntu 内读取 Windows 浏览器。需要 Windows 自己安装的 Python；如果 `python3` 不可用，把上面两行中的 `python3` 都换成 `python`。只需将这个脚本下载到 Windows 的文件夹，无需在 Windows 重新安装整套应用。

Linux / macOS 若提示系统 Python 不允许安装包，可先创建并启用独立环境，再执行上面两行：

```bash
python3 -m venv .venv-cookie
source .venv-cookie/bin/activate
```

成功后，当前文件夹会出现 **`bilibili_cookie.txt`**。用文本编辑器打开，复制里面的整行内容，按下方“通过网页绑定”粘贴到 **参与直播间 → 配置本人登录**。脚本不会在终端打印 Cookie，默认也**不会覆盖已有输出文件**。

按需选择参数：

| 参数 | 用法 |
| --- | --- |
| `--browser` | 默认 `chrome`；也可填 `edge`、`firefox`、`safari`、`brave` 或 `chromium`，选择实际登录的浏览器。 |
| `--cookie-file` | 可选，指定对应浏览器配置的 Cookie 数据库文件路径；路径有空格时加引号，用于选择非默认配置。 |
| `--output` | 可选，指定新的输出文件名或路径；例如 `bilibili_cookie_firefox.txt`。目标目录需要已经存在。 |

例如，导出 Firefox 的登录信息并另存为新文件：

```bash
python3 get_bilibili_cookie.py --browser firefox --output bilibili_cookie_firefox.txt
```

脚本只在本地读取、筛选并保存 Cookie，**不会发起网络请求，也不会验证登录是否仍有效**。它要求存在 `SESSDATA` 才保存；应用发送弹幕还需要 `bili_jct`。仓库已忽略 `bilibili_cookie*.txt`；使用其他输出名称时，也不要把登录文件提交到 Git。

读取失败时，先确认选择了正确浏览器与已登录的配置，可关闭浏览器后重试。若系统询问钥匙串访问，确认请求来自自己刚运行的 Python。浏览器加密机制可能使库无法读取；此时直接使用下面的手动方式。

#### 方法二：通过浏览器开发者工具复制

以 Chrome / Edge 为例：

1. 在自己信任的浏览器打开 [Bilibili 直播](https://live.bilibili.com/)，正常登录本人账号。
2. 打开一个直播间，按 `F12` 打开开发者工具，切换到 **Network / 网络**。
3. 刷新直播间，选中发往 `api.live.bilibili.com` 的正常请求；在 **Request Headers / 请求标头** 找到 `Cookie`。
4. 复制 Cookie 的值，不包含整段请求、不包含 `Authorization`、不复制响应中的 `Set-Cookie`。
5. 确认其中包含 `SESSDATA` 和 `bili_jct`。前者承载登录会话，后者用于发送接口的 CSRF 校验。

也可以在开发者工具 **Application → Cookies** 中查看本人 `bilibili.com` 域下的这两个值，再组成如下格式。下面仅为占位示例，不是可用账号：

```text
SESSDATA=YOUR_OWN_SESSDATA; bili_jct=YOUR_OWN_BILI_JCT
```

不要把 Cookie 放进 Issue、聊天截图、README 或 Git 提交；它不是项目下载所用的 GitHub Token。

### 方式 A：通过网页绑定（适合发送弹幕）

1. 启动应用并连接直播间。
2. 在播放器下方找到 **参与直播间**。
3. 点击 **配置本人登录**，把 Cookie 粘贴到输入框。
4. 点击 **保存登录**。输入框会立即清空，页面只展示是否已配置。
5. 选择候选弹幕或自行输入文本，再点击 **发送弹幕**。

Cookie 保存在本机 `data/bilibili_send_credentials.private.json`，权限为 `0600`；如果更改了 DATA_DIR，则保存在对应数据目录。它不会返回在 `/api/state` 中，不会被送给模型。页面保存只做格式检查，真正发送前会向 Bilibili 核实登录状态，因此“已配置”不等于 Cookie 永不过期。

修改账号时，重新保存本人新 Cookie 即可。本地保存值优先于 `.env` 的 BILIBILI_COOKIE。

### 方式 B：通过 `.env` 绑定

编辑 `.env`：

```dotenv
BILIBILI_COOKIE="SESSDATA=YOUR_OWN_SESSDATA; bili_jct=YOUR_OWN_BILI_JCT"
```

然后正常重启应用。此方式同时可供直播平台连接使用；如果平台要求登录后接收弹幕，优先使用此配置。

网页保存的发送 Cookie **不会自动替换当前接收连接**的 Cookie。只为发送设置登录时用方式 A；接收连接需要登录时用方式 B 并重启。

### 清除或更新绑定

重新保存会替换本地发送账号。也可以在本机清除网页保存的配置：

```bash
curl -X POST http://127.0.0.1:7862/api/danmaku/credentials \
  -H 'Content-Type: application/json' \
  --data '{"cookie":""}'
```

该操作只删除本地 Cookie 文件；如果 `.env` 仍有 BILIBILI_COOKIE，会回退使用环境配置。要完全取消绑定，需要同时清空 `.env` 的该项并重启。

发送被拒绝时查看页面提示：过期则更新 Cookie；需要验证码时回到官方直播间完成验证；禁言、频率限制等需按平台规定处理。程序不会绕过限制，也不会在超时后自动重发。

## 发送弹幕与实时候选

### 五条候选如何生成

候选生成会结合直播主题与房间标题，综合近 **30 秒**的：

- 多帧画面理解、动作变化与画面 OCR；
- 带源时间和不确定性标记的声音转写；
- 其他观众发送的弹幕。

另外，会从已接收、缓存的近 **5 分钟**弹幕历史中抽样最多 **24 条**，帮助延续直播间的话题与语气；本会话近 **30 分钟**内成功发送的最后 **12 条**也会作为参考，避免反复说同一句话。历史弹幕只是背景，不能代替当前的新鲜画面、声音或弹幕证据。接收缓存最多保留 300 条，繁忙直播间可能覆盖不足 5 分钟；本人已发记录保存在本地，恢复同一会话时继续沿用。切换直播间时清空这些历史，不会把上一间的聊天带过来。

默认约每 **12 秒**尝试更新一轮，具体还受模型耗时影响。输入使用有界的近期内容，某路暂时不可用时，只依据仍有效的来源生成，不编造缺失证据。观众说法与自动转写不会被当成无误事实。

自适应模式下，正在回答问题、两路观察都在处理，或理解已经明显落后时，候选会显示“稍后更新”。已有候选和手写草稿保留；资源空闲后再刷新，优先让同担跟上直播。若仅观察繁忙持续超过 30 秒，会允许一次最多 6 秒的候选尝试，避免功能一直暂停；用户提问仍优先。

**现场刷屏直接跟上。** 五条 AI 候选下方有独立的「大家在刷」小区域，展示最多三条近期集中重复的真实原句及出现次数，不占用 AI 候选。这项检测不调用模型，即使 AI 正在回答问题或模型尚未配置，也会更新；复读热度过去后移除。点击只填入原文，不会把计数带进草稿。启动「一键融入」后，也会从这些原句和有效 AI 候选中随机选择；现场原句发送前会重新检查是否仍在刷，已由本人成功发过的近期原句不重复发送。

检测查看最近 30 秒、最多 150 条接收记录：每句至少出现 4 次，占有效弹幕至少 15%；能取得用户标识时还要求至少 3 位不同观众，避免单人连刷触发。已知重复消息会去重。只有整段记录均无用户标识时才退回计数判断；这时无法确认是否来自不同观众。超长弹幕、平台表情标签、明显隐私或不合适的文本不会作为复读候选。计数仅来自程序收到的弹幕，不代表全站统计。

候选更新不会覆盖手写草稿。**默认采用手动发送：点击候选只是填入输入框，点击“发送弹幕”后才会发送。** 可以先编辑，再决定是否发送。下方的“一键融入”需要单独启动。

发送区域底部的 **已发送弹幕** 列表显示本次会话最近 **30 条**成功记录，最新在前，包含发送时间、内容和“手动发送 / 一键融入”来源。发送成功后实时更新，刷新页面或服务重启后恢复同一会话仍可查看；失败或结果未确认的请求不会标成已发送。升级前“一键融入”中已确认成功的记录可恢复，旧版未落盘的手动发送记录无法补回。

### 纯良还是开串：调整候选风格

候选区的风格滑杆从左侧**纯良**到右侧**开串**，范围为 **0–100**，默认 **30**。向左偏温和，向右增加玩梗和吐槽的语气；候选仍参考当前直播内容和弹幕记录。设置会保存在本地，切换直播间或重启服务后继续沿用。

最右侧的**开串指有幽默感的反串**：假装站在相反立场、一本正经说反话，或为眼前的失误找个荒诞理由。例如看到失误时假装护航：“不是失误，是给对面机会”。笑点来自直播里实际发生的反差，不靠“急了”“就这”等挑衅词堆强度，也不编造动作、引用或身份。内置提示和本地例句筛选都会按这个方向调整；词法筛选只能辅助判断，最终效果仍受模型和当前语境影响。现场「大家在刷」保留原文，不随滑杆改写。

拖动后，新设置应用于下一轮候选生成，旧风格候选立即失效；已经在生成的旧风格结果也不会重新生效。“一键融入”会等待新风格的 AI 候选，不会继续发送旧风格候选；仍在刷的现场原句可以照常选择。**风格在“一键融入”运行期间也可以调整**，无需停止；手写草稿不随滑杆变化而修改。

### 两种风格来源：内置风格与本地语料

在“参与直播间”的候选风格区选择来源；两种模式都能配合“纯良—开串”滑杆，切换后会作废旧候选并按新模式生成。来源设置会随风格强度一起保存，重启后沿用。

| 模式 | 适合什么情况 | 每轮使用的风格参考 |
| --- | --- | --- |
| **内置风格（默认）** | 下载后直接使用，没有自己的记录 | 应用自带的精简表达规则，不读取本地语料目录 |
| **本地语料** | 已有清洗后的弹幕或 Super Chat 记录，希望更贴近其表达 | 独立提示配合少量本地例句，按当前话题、风格强度和近期选用情况挑选 |

应用自带从真实弹幕记录中提炼的表达规则，位于 [`app/danmaku_voice.py`](../app/danmaku_voice.py)。短句、省略主语、接半句话、针对当前细节反应，会随“纯良—开串”滑杆改变语气。中长留言则提炼小请求、具体提问、预期与结果的转折，压缩为普通弹幕可发送的一句话；候选仍以正在发生的画面、声音和弹幕为依据。

这次参考了 8 份清洗记录、共 407,786 条文本，并按文件均衡、去重抽样，减少大文件和大量复读的影响。清洗时移除了类型字段，Super Chat 正文与普通弹幕混合保留，因此无法可靠区分两者，也不按长短认定 Super Chat。内置规则兼顾中长留言表达，不保存原始留言、人物身份、私人故事或房间专属话题。

**内置模式不需要语料 JSON，两种模式都不需要额外训练。** 内置规则和本地例句通过提示词影响本轮表达，不会微调模型权重。原有模型调用次数、输出上限和后台时间预算保持不变；本地模式的少量额外输入仍可能增加一些推理耗时。候选生成和“一键融入”仍发送普通弹幕，没有新增付费 Super Chat 发送功能。

#### 添加自己的 JSON

在项目文件夹内新建 `danmakus_style` 文件夹，把**已经清洗过**的 UTF-8 JSON 放进去，可同时放多份。推荐格式如下，示例句子为说明格式而编写：

```json
{
  "messages": [
    "这一句接得挺稳",
    "怎么又回到这里了",
    {"type": "superchat", "message": "这一段能再讲讲吗"}
  ]
}
```

也支持顶层字符串列表，以及 `messages` / `danmakus` 中带 `message` 或 `text` 字段的对象。只提取文本，不把 UID、用户名等字段加入参考。已明确标记 `type: "superchat"`、`"sc"`、`"paid"` 或 `paid: true` 的留言可保留一段简短表达；没有标记的文本不会仅凭长度被认定为 SC。

然后在网页选择 **本地语料**。界面显示索引中的文件数和参考条数；这是去重、过滤、限量后的样本数，不是 JSON 中全部弹幕的数量。连接直播后，候选循环会自动检查新增、修改或删除的文件，无需重启；两次检查至少间隔 5 秒，正常候选节奏下约下一轮检查。首次建立索引在后台进行，暂时没有可用参考时继续用内置规则；缺失目录、空文件或坏 JSON 也会回退，不影响观看和提问。

每轮最多参考 **6 条、每条不超过 48 字、合计不超过 192 字**。本地模式使用独立提示，以参考的句长、口头词、省略和接话方式决定表达，不叠加内置风格的固定句式；当前直播内容仍决定回应什么，滑杆调整调侃程度。历史人物与事件不作为当前事实，独特整句及其仅改标点的版本会过滤；“确实”“？”等通用短反应可以自然沿用，已经由本人发送过的内容仍去重。

索引同时保留常见短反应和较少见表达。样本足够时，每轮兼顾 3 条具体话题例句与 3 条不同类型的短反应，避免只检索到较长的描述，也避免笑声或问号的长度变体占满位置。不同文件之间均衡取样、轮换参考，频繁复读不会独占全部位置。匹配不足时可能只参考少量通用短反应，甚至不使用本地例句。风格强度匹配是词法近似，不是对每条原始弹幕的准确语气标注。

**本地 JSON 不随 GitHub 仓库上传，但选中的少量正文会发给你配置的模型接口。** `danmakus_style/` 整个目录和本地分析产物均已被 Git 忽略。程序会过滤方括号表情、明显联系方式、重复灌水等内容；这不等于完整匿名化，加入文件前仍需移除正文中的私人信息。

索引上限：最多 64 个文件、单文件 16 MiB、总文件大小 64 MiB；每文件最多 1,500 条，合计最多 12,000 条参考。支持最多 3 层子目录，不跟随符号链接。超过限制的文件会跳过，索引状态中会显示跳过数量；原始 JSON 保留原样。

### 一键融入：让同担也聊两句

在 **参与直播间 → 一键融入** 设置基准间隔和发送数量，然后启动，即允许程序使用本人已配置的登录账号，向当前直播间自动发送候选弹幕：

- 基准间隔以**秒**为单位，默认 **300**，允许 **5–3600 的整数**；发送数量默认 **6 条**，允许 **1–1000 的整数**。运行期间这两个输入框锁定；要修改，先停止，再设置并重新启动。
- 首条新候选就绪后立即发送，不先等待一个基准间隔。此后每轮独立从基准间隔的 **70%–130%** 范围内均匀随机抽取下一次计划间隔；相邻发送的等待从**上次成功发送完成后**开始计算。
- 例如填写 **300 秒**，抽取的计划间隔为 **210–390 秒**（3 分 30 秒至 6 分 30 秒）。这不是实际发送间隔的保证：缺少新鲜候选、网络等待等都可能让实际发送更晚，页面的“下一次计划时间”也不代表一定按时发出。
- **不设运行时限**，发送数量采用本次填写的值，成功发送到该条数后结束。例如填 **3 条**，成功发送第 3 条后结束；间隔较长或缺少候选时继续等待，不会因为超过 30 分钟而停止。未点击启动时不会自动发送。
- 从新鲜 AI 候选和「大家在刷」原句中选择；现场复读依据当前弹幕独立判断，不要求等待画面模型。缺少合适的新鲜内容时跳过，错过的发送不会补发，也不为凑足条数连续发送。
- 页面显示已发送条数、下一次计划时间、跳过次数和最近发送内容，手写草稿不会被覆盖。
- 点击 **停止融入**可结束本轮；切换直播间或主播下播时也会停止。服务重启后不会恢复“一键融入”，需要重新启动。
- 计时由服务端负责，关闭浏览器不代表停止；要提前结束，请点击 **停止融入**。发送失败或结果不明时停止，不自动重发。

“一键融入”仍使用同一套本人账号与平台发送规则。这里的发送计数表示 Bilibili 已受理请求，不能保证弹幕一定显示在直播间。

### 发送规则

- 当前默认限制 20 个 UTF-16 单元，普通汉字通常计 1，部分 Emoji 计 2。
- 请求携带当前会话 ID；切换房间后旧页面请求会被拒绝，避免误发到新房间。
- 成功提示“Bilibili 已受理发送请求”不保证平台一定展示这条弹幕。
- 发送请求不自动重试；超时可能意味着结果未知，应先在直播间确认。
- 使用本人的登录账号，程序不提供匿名发送或自动刷屏。

### 复制最近 2 秒的随机弹幕

点击 **复制近 2 秒随机弹幕** 后，程序从浏览器最近两秒实际收到的新弹幕中随机抽取一条并复制。

- 刷新页面加载的历史列表不算“刚收到”。
- 两秒内没有新弹幕时，显示提示，不用旧弹幕代替。
- 只执行复制，不自动填入发送框或发送。
- 浏览器不允许自动写入剪贴板时，会展示已选中文本，按 `Ctrl+C` / `Command+C` 手动复制。

## 声音、说话人和记忆

### 声音链路

后台复用已经完成的本地 HLS 分片提取 16 kHz 单声道 PCM，默认约 4 秒形成一个音频块，再进行 VAD、转写和声纹处理。声音队列最多保留两个待处理块，拥堵时优先跟上最新直播，不阻塞视频。

这是连续音频短块的异步转写，当前没有逐字临时字幕，也没有逐词强制对齐。唱歌、混音、背景视频、跨块句子都可能导致漏字或错字。用户可回听原始片段核实。

### 说话人分组

声纹以“说话人 A/B/…”匿名分组，不能证明真实身份或音源来自实时麦克风。

- 新声音需要至少两段一致有效声纹才确认，并回填首段。
- 已确认组保留有限多个参考，允许一定声音变化，弱匹配保留不确定标记。
- 短片段、混杂或模糊匹配仍可能显示“待定”。
- 当前最多保留 16 个说话人组；阈值为启发式，并非校准后的身份概率。
- 系统不会自动把第一个、最响或出现最多的声音认成主播。

### 绑定、改名与合并

声音面板中的来源可标为“主播 / 背景视频 / 歌声 / 来源不确定”：

1. **单段标记**只影响该片段，优先于说话人组的来源参考。
2. **说话人绑定**作为同声纹来源参考，立即进入记忆页和后续问答。
3. **改名**方便区分多个声音；不会修改实际身份事实。
4. **合并**用于人工确认的误拆分组，保留目标名称与单段人工标记。
5. 两个明确来源标签冲突时，需先调整标签再合并；不会因为两组都标“主播”就自动合并。

已提交的问题保留提交时的标记快照，后续绑定不会悄悄改写旧回答。声音参考和标签会在正常重启后恢复。

当前没有可靠的自动混音分离、歌曲分类或重叠说话检测。主播自己的录音和实时说话也可能得到同一声纹组；真正区分音源通常需要独立音轨或其他可靠证据。

## 时间对应与持续观察

直播播放、画面观察、声音识别与回答分别进行。反复提问不会暂停观察；取消一个问题也不会停止直播记录。每个问题使用提交时的记忆与声音标记，最多允许四个待处理问题。

默认每秒采样，后台观察从 4 帧开始，在最新缓存中动态选择 2 / 4 / 6 / 8 帧。应用根据实际推理耗时和观察更新间隔调整输入数量与提交频率，最多两路观察并行；尚未处理的窗口只保留最新一份。调整只作用于理解输入，不改变视频采集频率、HLS 分片或播放器位置。

音频识别需要先收集一个短片段。默认 `AUDIO_ALIGNMENT_WAIT_SECONDS=0.5`，且自适应模式会把等待上限限制为 0.5 秒，即使旧配置仍写着 4。先使用已经到达的同期声音；晚到转写按**原内容时间**独立补记到声音、观察与记忆时间线。看到“同期音频待到”或“部分到达”时，表示这次综合理解尚未获得完整声音，不能把画面已更新理解为声音也已全部理解。

播放器不会为了等文字而暂停。观察卡片和声音面板显示内容发生的时间区间，实际处理速度仍受网络、模型负载和硬件影响，繁忙时文字可能落后于正在播放的直播。

页面的“理解落后”会随时间增长：从最新有效画面观察的最后输入帧**在本机被收到**开始计时，直到现在。它同时反映生成耗时和等待下一条观察的时间；目标默认 15 秒，超过时诚实显示滞后，并继续保留已生成内容。历史会话刚恢复时显示等待新的观察，不把旧结果当成刚生成。观察卡片中的“处理滞后”仍是该条完成时的历史值，“模型推理”是模型请求耗时。

15 秒是调度目标，不是断网、模型过载时也保证持续输出的承诺。这些数字不含 Bilibili 上游/CDN 延迟，也不是主播到浏览器的端到端时延。系统不会为了符合数字而跳播、清空慢结果或改写内容时间。观察保留 `MODEL_TIMEOUT` 的失败超时，慢但有效的结果仍可发布并标为滞后；候选请求最多 6 秒，超时保留原有草稿。观察失败后降低输入负载再处理新画面。

如需使用原来的固定窗口方式，设置 `ADAPTIVE_OBSERVATION=0`；此时 `OBSERVATION_FRAMES` 与 `OBSERVATION_STRIDE` 决定固定窗口大小和步长，音频等待采用配置值。

## 配置项参考

下面覆盖主应用与启动脚本的配置。通常编辑项目根目录 `.env`，然后 `Ctrl+C` 停止应用并重新 `./start.sh`；`HOST` 和 `PORT` 是例外，写在启动命令前。

| 配置 | 默认值 / 含义 |
| --- | --- |
| MODEL_BASE_URL | 视觉服务地址，例 `http://127.0.0.1:8020/v1`；非空时优先 |
| MODEL_NAME | `Qwen3.8-27B-FP8`，须与模型服务暴露的名称一致 |
| MODEL_API_KEY | 视觉 API key；不要提交 |
| MODEL_ENDPOINT_FILE | 默认 `data/model_endpoint.json` |
| MODEL_TIMEOUT | 90 秒，最小 5 秒；视觉请求失败超时，独立于 15 秒新鲜度目标；候选另有 6 秒上限 |
| AUDIO_ENABLED | `1`；`0`、`false` 或 `no` 停止后台转写，播放器原声不受影响 |
| AUDIO_BASE_URL | 音频服务地址，例 `http://127.0.0.1:8021` |
| AUDIO_API_KEY | 音频服务 API key |
| AUDIO_ENDPOINT_FILE | 默认 `data/audio_endpoint.json` |
| AUDIO_ALIGNMENT_WAIT_SECONDS | 0.5 秒，允许 0–8；自适应模式最多等 0.5 秒，不延迟播放器 |
| FFMPEG_BIN | `ffmpeg`，也可设绝对路径 |
| SAMPLE_INTERVAL | 1 秒，最小 0.5 秒 |
| OBSERVATION_FRAMES | 4；固定窗口大小或自适应初始档位，也支持 2 |
| OBSERVATION_STRIDE | 3 个采样帧，允许 1–4；自适应模式由控制器安排提交节奏 |
| OBSERVATION_CONCURRENCY | 2，允许 1–2 |
| ADAPTIVE_OBSERVATION | `1` 开启动态选帧；`0`、`false` 或 `no` 使用固定窗口 |
| OBSERVATION_MAX_FRAMES | 8；可选 2 / 4 / 6 / 8，与仓库视觉服务的多图上限一致 |
| OBSERVATION_TARGET_LAG | 15 秒，允许 5–60；最新理解的持续新鲜度目标 |
| ROOM_POLL_SECONDS | 20 秒，最小 5 秒；房间开播状态轮询间隔 |

```text
    ├── audio/state.json             # 音频文字和公开标签
    ├── audio/state.private.json     # 声纹参考，0600
    └── audio/*.wav                  # 原始片段回听
```

### 默认保留范围

| 内容 | 有界保留 |
| --- | --- |
| 采样帧 | 最近 300 张；待处理问题/观察可临时保护额外帧 |
| 观察记录 | 最近 400 条，前端渲染最近部分 |
| 片段摘要 | 最多 80 个 |
| 重要事实 | 最多 40 条 |
| 对话 | 最多 80 条消息 |
| 音频证据 | 最多 200 段 WAV 与对应文字 |
| 声音参考 | 最多 16 组，参考向量单独私有保存 |
| HLS | 滚动分片和最多两代连接目录 |
| 事件日志 | 约 10 MiB 轮转，当前文件与四个备份 |

正常关闭进程后重启，会尝试恢复原活动房间、文字记忆、已完成对话、声音记录和手工绑定。进行中的问题不会续跑，旧采样帧缓存可能过期；已过期证据返回 HTTP 410，文字仍可保留。

网页点击“断开”会清除活动恢复指针。不同历史会话目录不会自动全部删除；应用不是完整录像系统，也不是无限归档系统。

如需迁移，请在正常停止 Web 服务后备份 DATA_DIR；其中包含本人 Cookie、音频、声纹参考和直播记录，应仅存放在自己信任的位置。模型权重较大，可分开备份或重新下载。

清理旧会话时先确认其 ID 并停止相关会话，删除对应 `data/sessions/<id>/` 目录；不要在运行中删除当前会话数据。删除整个 data 还会移除模型配置、登录信息及下载的权重。

## 常见问题

### 页面能打开，但模型没有输出

检查 `/api/health` 中的 configured，再执行页面模型检查。确认服务地址能从 **Web 应用所在机器** 访问，视觉地址带 `/v1`，模型名称、API key 与服务端一致。

configured=true 只代表填了配置。服务尚未加载完权重、GPU 显存不足、接口不支持多图/JSON 或 key 错误都可能导致推理失败。

### 配好了 `.env`，为什么还是访问旧服务？

非空 BASE_URL 优先于 endpoint JSON；应用进程的既有环境变量又可能优先于 `.env`。检查启动终端环境和两套配置，正常重启后重新确认。

### 无法播放，或者只有官方播放器能看

检查 FFmpeg、直播是否开播、服务器网络与平台连接提示。官方播放器能播放不代表后台 FFmpeg 采样成功；后台失败时不会生成虚假的观察。Bilibili 播放地址和接口可能变化，服务会退避重连。

### 能听到直播声音，但没有文字转写

播放器原声和后台转写是两条不同链路。确认 AUDIO_ENABLED、音频服务 `/analyze`、ffprobe、音轨存在状态及声音面板错误。音频服务离线不应阻止画面观察。

### 音频文字为什么仍有延迟？

需要累积音频块、等待 HLS 分片完成、执行转写和理解。页面按原内容时间归位，但不会把后台处理变成零延迟；播放器保持低延迟继续播放。

### 唱歌、音乐背景或多人同时说话识别不准怎么办？

当前短块 VAD/ASR 和声纹不是混音分离系统。优先回听原片段，手工标记来源；不要把歌声或混杂音频当成稳定身份参考。此版本未实现专门的歌声识别模式。

### 绑定主播后，为什么旧回答没有改变？

已提交的问题使用冻结快照，已完成回答保留当时证据。绑定会立即更新记忆并用于新问题；这是避免回答在后台无提示变化的设计。

### 为什么有“同期音频待到”？

视觉窗口对应的 ASR 尚未完成且有限等待已结束。程序继续理解画面，稍后按原时间记录声音，不使用前一段声音代替。

### 声纹经常出现待定，或者同一声音被拆成多组？

短语音、歌声、音色变化和混音都可能导致不确定。可选择清晰单人片段作为来源参考；人工确认误拆后在说话人编辑窗口合并。分组减少不等于身份准确率必然提高。

### Cookie 保存了，为什么无法发送？

保存只检查格式。确认是本人 Bilibili Cookie，至少包含 SESSDATA 和 bili_jct，并检查是否过期、需要验证、被禁言或触发频率限制。平台限制不能通过应用配置绕过。

### 随机复制为什么提示没有弹幕？

它严格只选浏览器刚收到的两秒内新弹幕；连接后加载的历史弹幕、较早弹幕和恢复状态均不会用来凑数。

### 历史证据为什么返回 410？

采样图和 WAV 有保留上限，正常重启也可能清理未注册的旧帧缓存。文字保留不保证音视频证据永久可用。

### 可以同时给多个用户分别看不同房间吗？

当前工作台只有一个共享活动会话。需要隔离房间时运行独立实例，并为每个实例设置不同的 DATA_DIR 和 PORT；不要增加 Uvicorn worker 数量来模拟多用户隔离。
